# ARCHITECTURE — 매칭 엔진 동작 원리

## 문제 정의

한글 음차 표기는 표준이 없다. 같은 와인을 사람마다 다르게 쓴다.

```
Château Talbot  ->  샤또 딸보 / 샤토 탈보 / 샤또 타르보 / 딸보
Chardonnay      ->  샤르도네 / 샤도네이 / 샤르도내
```

단순 문자열 비교로는 하나도 못 잡는다. 그렇다고 모든 변형을 사전에 나열하는 것도 불가능하다.
**변형의 규칙성을 이용해 정규화**하는 게 핵심 전략이다.

---

## 1단계: 자모 정규화

한글을 자모로 분해한 뒤, 음차에서 자유변이인 자모들을 하나로 접는다.

### 자음 접기

```
ㄲ ㅋ -> ㄱ     ㄸ ㅌ -> ㄷ     ㅃ ㅍ -> ㅂ     ㅉ ㅊ -> ㅈ     ㅆ -> ㅅ
```

원어의 무성 파열음을 한글로 옮길 때 표기자마다 갈리는 지점이다.
`딸보`와 `탈보`는 이 단계에서 **같은 키가 되어 1.00 정확 매칭**으로 잡힌다.

### 종성을 초성과 같은 코드포인트로 통일

NFD 분해 시 같은 자음도 위치에 따라 다른 코드포인트를 받는다.
`말`의 받침 ㄹ은 U+11AF, `르`의 초성 ㄹ은 U+1105다.

이걸 통일하지 않으면 `탈보` vs `타르보`가 "삽입 1회"가 아니라
"치환 + 삽입"으로 계산되어 거리가 4배 이상 뛴다.

> 이 버그는 실제로 있었고, 고치기 전 ㄹ분리 케이스 정확도가 75%였다.
> 수정 후 100%. ㄹ만의 문제가 아니라 **받침이 들어간 모든 비교**에 영향이 있었다.

### 모음 접기

```
ㅐ -> ㅔ     ㅒ -> ㅖ     ㅚ ㅙ -> ㅞ          (현대 한국어에서 변별력 상실)
ㅑ -> ㅏ     ㅕ -> ㅓ     ㅛ -> ㅗ    ㅠ -> ㅜ  (반모음 자유변이)
```

반모음 접기 덕에 `쪼/쬬`, `자코모/지아코모`, `산조베제/산지오베제`가 자동 흡수된다.

### 초성 ㅇ 제거

음가가 없는데 자모 한 칸을 차지해 거리 계산을 왜곡시킨다.

---

## 2단계: 가중 편집거리 (Damerau-Levenshtein)

정규화로 흡수되지 않는 차이는 편집거리로 근사한다. 단, 균등 가중치를 쓰지 않는다.

### 저비용 자모 (0.3)

```
ㅡ  ㅜ  ㄹ
```

원어 자음군을 한글로 풀 때 생기는 **잉여 모음**이라 삽입·삭제 페널티를 깎는다.
`탈보`(다ㄹ보) vs `타르보`(다르보)의 차이가 여기 해당한다.

### 자리바꿈 (0.6)

인접 자모가 뒤바뀐 경우. `다브루초` vs `다부르초`처럼 ㅡ/ㅜ가 도치되는 일이 잦다.
일반 Levenshtein은 이를 "삭제 + 삽입" 2회로 세어 실제 체감보다 훨씬 멀게 평가한다.

---

## 3단계: 3중 조회 전략

```
1) 완전 일치      정규화 키가 정확히 같음                     -> 1.00
2) 접두/토큰 일치  타이핑 중이거나 일부만 입력                 -> 0.80~0.97
3) 오타 보정      위 둘이 전부 실패했을 때만 편집거리 계산      -> 임계값 이상
```

### 왜 접두사 매칭이 별도로 필요한가

편집거리만 쓰면 `몬테`로 `몬테풀치아노`를 찾을 수 없다. 뒷부분이 통째로 빠져
유사도가 임계값 아래로 떨어지고, 길이 차 가지치기에도 걸린다.

검색어 자동완성은 **부분 입력을 정상으로 취급**해야 하므로 별도 경로가 필요하다.

### 왜 토큰 인덱스가 필요한가

접두사 매칭은 문자열 **앞**에서만 일치를 본다.
사전 키는 공백이 제거된 통짜(`무동로지ᄅ드`)라 `로칠드`(뒷어절)로는 절대 못 찾는다.

그래서 한글 이름을 **어절 단위로도 인덱싱**한다(`r.kt`).
점수는 이름 전체가 아니라 **그 어절 안에서의 덮는 비율**로 매긴다.
전체 길이로 나누면 뒷단어 검색이 항상 불리해져 후보에 오르지 못한다.

```
로칠드   -> Mouton Rothschild, Lafite Rothschild  (0.95)
세귀르   -> Calon-Ségur, Phélan Ségur             (0.95)
바주     -> Lynch-Bages                            (0.95)
```

### 다어절 질의의 함정

`샤토 디샹`을 조각으로 훑을 때 `샤토`가 수백 개 샤토를 전부 후보로 끌어와
정답을 파묻는다. 그래서 **중간 조각에서는 접두사 매칭을 끈다.**
단 마지막 조각은 타이핑 중일 수 있으므로 허용한다.

## 영문(로마자) 조회

한글과 별개 경로다. 핵심 차이는 **토큰 경계 보존**.

`ke` 필드는 공백을 유지한 채 저장된다(`trebbiano dabruzzo`).
통짜로 이어붙이면 `dabruzzo` 같은 뒤 토큰이 22자 덩어리 속 부분 문자열로만 잡혀
점수가 낮게 나온다. 토큰 단위로 비교해야 짧은 질의도 정당한 점수를 받는다.

하이픈 결합어(`Calon-Segur`)는 검색 키에서 한 단어로 붙지만,
사용자는 뒷부분(`segur`)만으로도 찾는다. 표시명에서 하이픈 조각을 추가 토큰으로 뽑는다.

## 한영 자판 오입력 복구

영타로 치려다 한글 모드면 `cabernet`이 `ㅊ뮫굳ㅅ`으로 들어온다.

자모를 QWERTY 위치로 되돌려 영문 질의로 복원한다.
겹받침(ㄺ→fr)과 복합모음(ㅘ→hk)은 두 글자로 풀어야 해서 별도 테이블을 둔다.

한글 조회가 먼저 실패했을 때만 시도한다.

---

## 정밀도 슬라이더

접두사 매칭 점수는 `0.80 + 0.20 × (입력이 이름을 덮는 비율)`이다.

슬라이더를 올리면 입력이 이름 전체를 덮는 항목만 남고,
낮추면 앞부분만 맞아도 후보에 오른다.

> 초기 구현에서는 슬라이더 범위가 0.60~0.95였는데 **0.60~0.85 구간이 죽어 있었다.**
> 접두사 점수의 최소값이 0.80이라 그 아래는 도달 불가능한 영역이었다.
> 측정해서 발견하고 범위를 0.80~0.99로 재설정했다.

오타 보정은 정밀도와 무관하게 일정 수준을 유지한다(상한 0.88).
상한이 없으면 정밀도를 올렸을 때 접두사 후보가 사라진 자리를 오타 후보가 채워
결과 개수가 **다시 늘어나는** 역전 현상이 생긴다.

## 성능

3,100행 사전에서 질의당 **1~2ms**. 별도 최적화 불필요.

- 정확 매칭은 `Map` 조회라 O(1)
- 검색 키(`key_ko`, `key_en`)를 빌드 시점에 미리 계산해 저장
- 편집거리는 길이 차 가지치기로 대부분의 후보를 건너뜀
