## 애플리케이션 스코프 (결정 필요)

여기부터는 **아직 정하지 않은 영역**이다. 세 가지 방향이 있고, 셋 다 할 필요는 없다.

### 방향 A: 검색 라이브러리 (npm 패키지)

가장 작고 확실한 범위. 매칭 엔진을 패키지로 떼어내 다른 프로젝트에서 가져다 쓴다.

```js
import { WineMatcher } from '@wine/matcher';
const m = new WineMatcher(terms);
m.search('샤또 딸보');  // -> [{ en: 'Chateau Talbot', score: 1.0, type: 'producer' }]
```

- 장점: 범위가 명확하고 테스트하기 쉽다. 셀러 앱이든 뭐든 재사용 가능
- 단점: 그 자체로는 사용자에게 보이는 게 없다

### 방향 B: 셀러 관리 PWA

이 사전을 **입력 보조 수단**으로 쓰는 실사용 앱.

- 와인 등록 시 한글로 치면 원어명 자동 완성
- 셀러 목록·빈티지·구매처·시음 노트
- 라벨 사진 촬영 → OCR → 사전 매칭
- 오프라인 동작 (Service Worker가 사전을 캐시)

- 장점: 실제로 쓰는 물건이 나온다
- 단점: 범위가 크다. 데이터 저장·인증·동기화 결정이 필요

### 방향 C: 사전 관리 도구 (내부용)

seed 데이터를 웹에서 편집하고 검증하는 관리 화면.

- 항목 추가/수정 시 실시간 중복·오류 검사
- 검색 테스트를 옆에 붙여 즉시 확인
- 변경 이력

- 장점: 사전 품질 향상 속도가 빨라진다
- 단점: 사용자가 나 혼자면 CSV 직접 편집으로도 충분할 수 있다

### 권장 순서

**A → B**를 권한다. A는 어차피 B의 부품이고, A를 먼저 하면 B의 범위가
"UI와 데이터 저장"으로 좁혀져 판단이 쉬워진다.

**C는 구현됐다.** 배포 페이지 우상단 톱니바퀴가 그 관리 화면이다 — 추가·수정·삭제가
즉시 사전에 반영되고, 중복·고아 별칭·캐노니컬 병합 위험을 제출 시점에 막는다.
원천이 Supabase로 옮겨가면서(D12) "CSV 직접 편집으로 충분하다"는 전제가 사라졌기 때문이다.

| 브라우저 | 모바일 우선 | 실사용은 대부분 폰 |

## 명시적 비목표

혼선을 막기 위해 **하지 않을 것**을 적는다.

- **와인 평점·가격 데이터 수집**: Vivino 등의 데이터를 긁어오지 않는다. 이 프로젝트는
  이름 매칭까지만 담당한다
- **전 세계 와인 완전 수록**: 롱테일은 원리적으로 불가능하다. 국내 유통 상위 커버리지가 목표
- **다국어**: 한국어 ↔ 원어만 다룬다. 일본어·중국어 음차는 범위 밖
- **검색 질의의 서버 왕복**: 검색은 전량 클라이언트에서 처리한다. 서버(Vercel 함수 +
  Supabase)는 사전 **편집·발행 경로에만** 존재하며 검색 경로에는 없다
  (이전 판의 "서버를 두지 않는다"는 Supabase 이관으로 폐기됐다 — `docs/DECISIONS.md` D12)

## 성공 기준

애플리케이션이 "됐다"고 말할 수 있는 조건:

1. 실제 셀러 와인 30개를 한글로 입력했을 때 **80% 이상**이 원어명으로 잡힌다
   (현재 프록시 테스트 기준 이미 달성. 실제 셀러 데이터로 재측정 필요)
2. 회귀 테스트(신의 물방울 329건, 파커 16건)가 계속 통과한다
3. `audit.py`의 "오류 의심" 항목이 0건이다
