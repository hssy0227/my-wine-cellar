# DECISIONS — 설계 판단과 근거

코드를 보면 "무엇을" 하는지는 알 수 있지만 "왜 그렇게" 했는지는 알 수 없다.
이 문서는 되돌리기 쉬운 판단들의 근거를 남긴다.

각 항목은 **당시 상황 → 판단 → 근거** 순으로 적었다.
나중에 상황이 바뀌면 판단도 바뀔 수 있다. 그때 이 문서를 갱신한다.

---

## D1. 규칙 기반 음차 변환기를 폐기했다

**상황**: 원어명 2,500건에 한글 표기가 비어 있었다. 자동 생성을 시도했다.

**판단**: 규칙 기반 변환기(`translit.py`)를 만들었다가 폐기하고 빈칸으로 남겼다.

**근거**: 결과 품질이 쓸 수 없는 수준이었다.

```
Chardonnay -> 슈알드옹나이   (정답: 샤르도네)
Merlot     -> 므에로트       (정답: 메를로)
Riesling   -> 르이스린그     (정답: 리슬링)
```

6개 검증 케이스 중 2개만 맞았다. 로마자와 발음의 관계가 불규칙해서
규칙으로는 잡을 수 없다. **틀린 표기로 사전을 오염시키느니 비워두는 게 낫다.**

**예외**: 미국 AVA는 96% 성공했다(`anglicize.py`). 영어 지명이
"고유명사 + 지형어(Valley, Mountain, Creek)" 조합이라 **조립이 가능**했기 때문이다.
품종명에는 그런 구조가 없다.

**되돌린다면**: LLM 배치 생성 + 사람 검수 방식. 200건씩 끊어 생성하고
눈으로 훑어 고치면 30분에 200건 처리 가능하다. 다만 음차는 정답이 하나가 아니라
(몽라셰/몽라쉐) 사람 판단이 반드시 필요하다.

## D2. 임베딩 대신 자모 정규화를 선택했다

**상황**: 초기에 "시맨틱 검색"을 검토했다.

**판단**: 임베딩을 쓰지 않고 자모 단위 규칙 + 편집거리로 갔다.

**근거**: 음차 고유명사에서 임베딩은 잘 작동하지 않는다.
"딸보"와 "Talbot"은 의미 공간에서 가깝지 않다. 이건 의미 문제가 아니라 **표기 문제**다.

자모 정규화는 결정론적이고, 디버깅 가능하고, 1~2ms에 끝나고, 오프라인에서 돈다.
임베딩은 이 중 어느 것도 보장하지 못한다.

## D3. Wikidata의 `ko` 라벨을 대부분 버렸다

**상황**: Wikidata SPARQL로 3,746행을 수확했다. `ko` 라벨이 1,171건 있었다.

**판단**: 그중 1,020건을 버리고 113건만 썼다.

**근거**: `ko` 라벨의 86%가 **한글이 아니라 로마자 복사본**이었다.

```
ko 라벨: "Ansonica", "Pelaverga", "Valle d'Aosta"  ← 한글이 아님
```

로마자↔로마자 매칭은 목적에 무의미한데 골드셋의 대부분을 차지해
측정을 왜곡시켰다. 한글 여부를 검사해 걸러냈다.

**남은 교훈**: 외부 데이터는 스키마가 맞아도 내용이 기대와 다를 수 있다.
수확 직후 반드시 내용을 눈으로 확인한다.

## D4. 생산자 계층에 집중했다

**상황**: Wikidata는 품종·지역을 잘 커버하지만 생산자는 거의 없었다.

**판단**: 생산자 사전을 수작업으로 만드는 데 가장 많은 노력을 들였다 (0 → 1,048건).

**근거**: 측정해보니 **커버리지 병목이 정확히 거기였다.**

| 단계 | 히트율 |
|---|---|
| Wikidata만 | 20% |
| + 지역/품종 보강 | 64% |
| + 생산자 421건 | **80%** |

Wikidata가 잘 커버하는 계층(품종)이 하필 실용 가치가 가장 낮았다.
Vivino 조회에 필요한 건 품종이 아니라 생산자·퀴베다.

## D5. 퀴베를 생산자와 분리해 등록했다

**상황**: "카뤼아드 드 라피트", "몬포르티노" 같은 세컨드 와인·단일 밭 이름 처리.

**판단**: 생산자와 별개 검색어로 등록했다.

**근거**: 사람들은 생산자명 없이 퀴베명만 부르는 경우가 많다.
사시카이아, 마세토, 솔라이아, 그랜지가 대표적이다.
"카뤼아드"만 쳐도 라피트 세컨드가 나와야 한다.

---

## D6. 등급(tier)을 지우지 않고 별도 필드로 분리했다

**상황**: `Chianti Classico DOCG`에서 DOCG를 검색 키에서 빼야 했다.

**판단**: 처음엔 원어명에서 통째로 지웠다가, **되돌려서 `tier` 필드로 보존**했다.

**근거**: 지우면 등급 정보가 소실된다. 검색어로는 안 쓰이지만
표시·필터링에는 필요하다. Chianti와 Chianti Classico는 다른 와인이다.

```
name_en:      Chianti Classico    ← 검색 대상
name_display: Chianti Classico    ← 표시
tier:         DOCG                ← 별도 보존
```

## D7. 계층을 Wikidata P131이 아닌 도메인 지식으로 정의했다

**상황**: 산지 계층(국가→광역→지구→마을)을 만들 때 Wikidata의
`P131`(상위 행정구역)을 쓸 수 있었다.

**판단**: 쓰지 않고 직접 정의했다.

**근거**: 행정구역과 와인 산지 계층이 일치하지 않는다.
포이약은 행정상 지롱드 주 소속이지만 와인 계층에서는 메독 아래다.
자동화하면 틀린 계층이 나온다.

---

## D8. 정밀도 슬라이더 범위를 0.60~0.95에서 0.80~0.99로 바꿨다

**상황**: 슬라이더가 있는데 움직여도 결과가 안 바뀐다는 지적을 받았다.

**판단**: 측정해보고 범위를 재설정했다.

**근거**: 실측 결과 **0.60~0.85 구간이 죽어 있었다.**

| 임계값 | 0.6 | 0.7 | 0.8 | 0.85 | 0.9 |
|---|---|---|---|---|---|
| "몬테" 결과 수 | 10 | 10 | 10 | 10 | 6 |

접두사 매칭이 고정 점수(0.90+)를 주고 있어 그 아래는 도달 불가능한 영역이었다.
점수 공식을 `0.80 + 0.20 × 덮는비율`로 바꾸고 범위도 실제 유효 구간으로 맞췄다.

**교훈**: UI 컨트롤은 만든 뒤 **실제로 작동하는지 측정**해야 한다.
있어 보이지만 아무 일도 안 하는 컨트롤이 생기기 쉽다.

## D9. 검증 장치를 먼저 만들고 데이터를 확장했다

**상황**: 사전을 대폭 확장해달라는 요청을 받았다.

**판단**: 바로 확장하지 않고 `audit.py`(무결성 점검기)를 먼저 만들었다.

**근거**: 그때까지 발견된 오류가 전부 같은 패턴이었다.

```
원어명 유실     "모스카토 다스티" -> "Moscato"     (d'Asti 소실)
타입 오분류     지역인데 producer 태그
동의어 중복     Garnacha / Grenache 가 별개 캐노니컬
```

이 오류들은 전부 **화면에서 이상한 걸 본 뒤에야** 발견됐다.
300건을 넣고 나중에 찾는 것보다, 잡아내는 그물을 먼저 치는 게 낫다.

실제로 `audit.py`를 만들자마자 기존 데이터에서 타입 오류 7건이 즉시 나왔다.

## D10. 동명이인은 허용한다

**상황**: `Norton`이 품종(미국 교배종)이면서 생산자(Bodega Norton)로 중복 등록됐다.

**판단**: 오류로 보지 않고 그대로 뒀다.

**근거**: 실제로 같은 이름을 쓰는 서로 다른 대상이다.
`Margaux`(지역 + 샤토명), `Montepulciano`(품종 + 지역)도 마찬가지다.

`audit.py`는 이런 케이스를 "확인 필요"로 표시하되 오류로 단정하지 않는다.
사람이 판단할 영역이다.

## D11. 접두어 제거 별칭을 자동 생성한다

**상황**: "디켐"을 검색하면 안 나오는데 "샤토 디켐"은 나왔다.

**판단**: 생산자 이름에서 선두 일반명사(샤토/도멘/테누타 등)를 뗀 축약형을
빌드 시점에 자동 생성한다 (454건).

**근거**: 길이 차 가지치기 때문이었다. "디켐"(자모 5)과 "샤토 디켐"(자모 9)은
차이가 4로 문턱(3)을 넘어 **비교조차 되지 않았다.**

사람들은 "샤토"를 자주 생략한다. 수작업으로 454개 별칭을 넣는 대신
규칙으로 생성하는 게 유지보수에 유리하다.

## D12. 사전의 원천을 Supabase로 옮기고 git은 export 사본으로 강등했다

**상황**: 편집하려면 seed CSV를 고쳐 PR을 만들고 머지해야 했다. 게다가
`demo/index.html`이 사전을 통째로 인라인한 스냅샷이라, 머지해도 배포 페이지의
검색 결과는 바뀌지 않았다 — 끊어진 연결고리가 있었다.

**판단**: Supabase(Postgres)를 원천으로 삼는다. 관리 패널에서 편집하면 즉시
재빌드·재발행되어 배포 페이지에 반영된다. git에는 GitHub Action이 export한다.

**근거**: 즉시 반영을 원하면 페이지가 데이터를 런타임에 받아야 하고, 그러려면
어딘가 원천이 있어야 한다. 다만 git을 버리지 않은 게 핵심이다:

- 회귀 테스트(`test_sync.py`·`matcher.test.js`)의 **골든 데이터가 `data/dist/`** 다
- Supabase가 정지·삭제돼도 사전을 복구할 수 있는 완전한 사본이다
- 페이지의 최후 폴백이다 (Supabase 장애 시에도 첫 방문자가 사전을 받는다)

그래서 동기화 실패는 조용히 넘어가지 않고 이슈를 연다. 이게 없으면 CI가 낡은
데이터로 통과하면서 실서비스와 어긋나는 상태를 아무도 모르게 된다.

**버린 것**: PR 리뷰 단계. 편집이 바로 라이브로 간다. 대신 `edit_log`로 사후
추적하고, audit이 잡은 신규 이슈를 제출 직후 화면에 띄운다.

`REQUIREMENTS.md`의 비목표 "실시간 서버 API — 서버를 두지 않는다"는 이 결정으로
폐기됐다. 다만 **검색 경로에는 여전히 서버가 없다** — 서버는 편집·발행 경로에만 있다.

## D13. 파생 로직은 build.py 한 곳에만 두고, SQL에는 검증만 맡긴다

**상황**: Postgres로 옮기면서 `search_key_en`을 `unaccent`+`regexp_replace`로
구현해 생성 컬럼으로 두면 깔끔해 보였다.

**판단**: 하지 않는다. `terms.key_en_norm`은 Python이 계산해서 넣고, DB는
모양(`^[a-z0-9 ]*$`)만 검사한다. `CHECK` 제약이 Python 검증과 겹치는 것은 허용한다.

**근거**: 실패 양상이 다르다. 중복된 **검증**이 어긋나면 제약 위반으로 요청이
거부된다 — 시끄럽고 즉시 발견된다. 중복된 **파생**이 어긋나면 검색 결과만 조용히
틀린다 — 규칙 1의 가야→Cowra 사고가 정확히 그 유형이다. `d'Abruzzo`나
`Pontet-Canet`에서 SQL과 Python이 한 글자만 갈려도 유니크 인덱스가 오염된다.

같은 이유로 증분 파생도 하지 않는다. canonical_id·대표 표기·별칭 정리는 전부
전체집합 함수라, 증분은 최적화가 아니라 두 번째 구현이 된다. 0.66초를 아끼자고
규칙 1을 깨지 않는다.

**부수 효과**: 쓰기마다 2,762행을 전량 재빌드한다. 측정해보니 콜드 ~5.8초
(pandas import 4.24초가 지배), 웜 ~1.6초. 사람이 버튼을 누르는 작업이라 수용 가능하다.

## D14. 사전 payload를 내용주소 불변 객체로 발행한다

**상황**: 페이지가 사전을 런타임에 받게 되면 캐시 무효화 문제가 생긴다. 오프라인
요구사항도 지켜야 한다.

**판단**: 파일명에 내용 해시를 넣는다(`wine_terms.<sha12>.json`). 이 객체는
`immutable`로 1년 캐시하고, 버전을 알리는 `manifest.json`만 `no-cache`로 둔다.

**근거**: URL이 내용을 유일하게 결정하므로 **캐시 히트는 정의상 정답**이다.
Service Worker가 조건부 요청조차 없이 cache-first로 돌려줄 수 있고, 그래서
네트워크가 완전히 없어도 즉시 검색된다. 덤으로 빌드 결과가 같으면 버전도 같아서
클라이언트가 헛되이 556KB를 다시 받지 않는다.

**함정 둘**(구현 중 실제로 밟았다):

- SW를 `/demo/sw.js`로 등록하면 스코프가 `/demo/`라 루트로 서빙되는 페이지를
  통제하지 못한다. 루트로 옮겨야 한다. 브라우저 HTTP 캐시가 우연히 비슷하게
  동작해서 겉으로는 되는 것처럼 보이기 때문에 놓치기 쉽다.
- 첫 방문 때 사전 fetch가 SW 활성화보다 먼저 끝나 캐시에 안 들어간다.
  페이지에서 Cache API로 직접 넣어야 한다.

**남은 제약**: iOS Safari는 7일간 미방문 시 캐시를 삭제한다(ITP). 홈 화면에
추가하면 면제되므로, `manifest.webmanifest`와 그 안내는 장식이 아니라 요구사항이다.
